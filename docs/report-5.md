# Отчёт: оценка «5» — SDD + Valkey, сравнение с вайбкодингом

## Задача
То же приложение для подготовки к экзамену, что и в `vibe/`, но сделанное по Spec-Driven Development
с помощью [GitHub Spec Kit](https://github.com/github/spec-kit) и агента opencode, плюс кэш на Valkey.
Код — в папке [`sdd/`](../sdd/).

## Кэш на Valkey

- Сервис `valkey` (valkey/valkey:8.0.13-alpine) в `compose.yaml`, с healthcheck и паролем.
- Django подключается через встроенный `django.core.cache.backends.redis.RedisCache` (Valkey совместим с протоколом Redis).
- Кэшируются: список тем с количеством вопросов, таблицы лидеров, лучшие результаты пользователя.
- Шаблон cache-aside: сначала кэш, при промахе — база и запись в кэш.
- Сброс кэша — сигналами Django через `transaction.on_commit`, только после реального сохранения в БД; отдельный хелпер для массовых операций (`update()`, `bulk_create()`), на которые сигналы не срабатывают.
- Если Valkey недоступен — ошибка пишется в лог, данные берутся из базы, сайт не падает.

### Доказательства

Все три сервиса запущены:

```
sdd-db-1       postgres:17-alpine            Up (healthy)
sdd-valkey-1   valkey/valkey:8.0.13-alpine   Up (healthy)
sdd-web-1      ...                           Up   0.0.0.0:8001->8000/tcp
```

Тесты кэша (`manage.py test exams.tests.test_cache_invalidation exams.tests.test_cache_fallback -v 2`) — 6 из 6 OK:

| Тест | Что проверяет |
|---|---|
| `test_topics_list_is_cached_and_invalidated_after_commit` | список тем кэшируется и сбрасывается после commit |
| `test_result_caches_are_invalidated_after_attempt_completion` | после завершения теста результаты и лидеры актуальны сразу |
| `test_direct_write_helper_invalidates_cache_after_update` | сброс кэша при массовых изменениях |
| `test_rollback_does_not_invalidate_cache` | откат транзакции не трогает кэш |
| `test_pages_fall_back_to_database_when_cache_fails` | при недоступном Valkey страницы отдаются из БД |
| `test_failed_invalidation_does_not_break_database_write` | ошибка кэша не мешает записи в БД |


Всего тестов в SDD-версии: **31, все проходят**.

## Сравнение: вайбкодинг и SDD

| Критерий | Vibe (`vibe/`) | SDD (`sdd/`) |
|---|---|---|
| Время до рабочего сайта | ~25 минут, 1 промпт + «продолжи» | несколько часов, большая часть — документы и их ревью |
| Нагрузка на бесплатную модель | один раз упёрся в дневной лимит | заметно больше запросов (документы + 43 задачи) |
| Когда найдены проблемы | после написания кода, на ревью и ручных проверках | до кода: на ревью спеки и плана и в `/speckit.analyze` |
| Безопасные настройки (DEBUG, `.dockerignore`, gunicorn) | добавлены вторым промптом после ревью | заложены с самого начала через конституцию |
| Пароль на кэш / доп. сервисы | — | Valkey закрыт паролем |
| Тесты | 17 → 19 после исправлений | 31, включая кэш, отказ Valkey и триггер БД |
| Целостность данных | уникальность вопросов, один правильный ответ | + 2–6 вариантов на уровне БД, статусы попыток, снимки вопросов в JSON |
| Прослеживаемость | промпты в журнале | требование (FR) → задача (T0xx) → коммит фазы |
| Продолжение после лимита модели | нужно объяснять агенту контекст | прогресс в `tasks.md`, достаточно «продолжи с первой невыполненной задачи» |
| Сложность кода | проще, быстрее читается | сложнее (триггер через RunSQL, снимки, сервисный слой), но надёжнее |

### Наблюдения
- Ревью на бумаге дешевле ревью кода: несостыковки (порядок задач, сброс кэша при массовых операциях, недоступные маршруты) исправлялись правкой одной строки в документе.
- `/speckit.analyze` недетерминирован: повторный запуск находит новые замечания. Нужно правило остановки — CRITICAL = 0 и закрытые HIGH.
- Агент иногда нарушает собственные правила (технологии в спеке, английские описания задач) — конституция и ревью это ловят.
- Бесплатные модели иногда «срываются» (иероглифы в ответе), на артефакты это не повлияло.

## Вывод
Вайбкодинг выигрывает по скорости и подходит для прототипа. SDD требует больше времени и запросов к модели,
но даёт продуманные требования, проверенные до написания кода, вдвое большее покрытие тестами, безопасные
настройки с первого коммита и прозрачную связь «требование → задача → коммит». Для учебного проекта на
один вечер достаточно вайба; для того, что будут поддерживать и развивать, оправдан SDD.
